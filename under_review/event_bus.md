# Event Bus Pattern

## 한 줄 정의

발행자와 구독자가 서로를 모른 채, 중앙 이벤트 버스를 통해 이벤트를 주고받는 패턴.

## 언제 사용하는가

- **컴포넌트 간 완전한 분리가 필요할 때**: Observer 패턴에서는 Subject가 Observer 목록을 직접 관리하지만, Event Bus에서는 발행자가 구독자의 존재조차 모름
- **다대다 이벤트 통신이 필요할 때**: 여러 발행자의 이벤트를 여러 구독자가 받아야 하는 경우
- **모듈 간 의존성 없이 통신해야 할 때**: 마이크로서비스, 플러그인 시스템 등에서 모듈이 독립적으로 배포/개발되는 경우

### 실제 사용 사례

- 메시지 큐 시스템 (RabbitMQ, Kafka의 단순화된 형태)
- GUI 이벤트 시스템 (이벤트 이름으로 발행/구독)
- 게임 엔진 이벤트 (적 사망, 아이템 획득 등의 이벤트를 전역으로 브로드캐스트)
- Django signals (`post_save`, `pre_delete` 등)

## 핵심 구조

**Observer 패턴과의 차이** — Observer는 Subject가 직접 Observer 목록을 관리한다. Event Bus는 중앙 버스가 이벤트별 구독자 목록을 관리하므로, 발행자와 구독자가 서로를 전혀 모른다.

**구독** — 이벤트 이름에 콜백을 등록한다.
- `EventBus.subscribe(event_name, callback)` → 구독

**발행** — 이벤트를 발행하면 해당 이벤트를 구독한 모든 콜백이 호출된다.
- `EventBus.publish(event_name, data)` → 등록된 모든 콜백 호출

## 주의할 점

- **디버깅 어려움**: 이벤트 흐름이 코드에 명시적으로 드러나지 않아서 추적이 어려움
- **순서 보장 없음**: 구독자 호출 순서에 의존하면 안 됨
- **메모리 누수**: 구독 해제를 빼먹으면 콜백이 계속 남아있음
- **Mediator와의 차이**: Mediator는 컴포넌트 간 구체적인 조율 로직을 가지지만, Event Bus는 단순 이벤트 전달만 담당
