# Chain of Responsibility Pattern

## 한 줄 정의

요청을 처리할 수 있는 객체들을 체인(사슬)으로 연결하고, 요청을 체인을 따라 전달하여 처리할 수 있는 객체가 처리하는 패턴. 고객센터 전화처럼 "담당자를 찾을 때까지 다음으로 넘기기".

## 언제 사용하는가

- **요청을 처리할 객체가 런타임에 결정될 때**: 어떤 핸들러가 처리할지 미리 알 수 없고, 요청 내용에 따라 달라지는 경우
- **여러 객체에게 처리 기회를 주고 싶을 때**: 첫 번째 핸들러가 못 하면 다음, 그 다음으로 넘기는 방식
- **처리 순서를 유연하게 바꾸고 싶을 때**: 체인의 순서나 구성을 런타임에 변경할 수 있음

### 실제 사용 사례

- 웹 미들웨어 체인 — Django/Flask의 요청 처리 파이프라인 (인증 → 로깅 → 요청 처리)
- 로그 레벨 필터 — DEBUG → INFO → WARNING → ERROR 순으로 적절한 레벨이 처리
- 결재 시스템 — 금액에 따라 팀장 → 부장 → 이사 순으로 결재 권한 확인
- 이벤트 버블링 — DOM에서 클릭 이벤트가 자식 → 부모 순으로 전파

## 핵심 구조

**Handler** — 요청을 처리하는 인터페이스. 다음 핸들러에 대한 참조를 가지고 있다.
- `handle(request)` → 자신이 처리할 수 있으면 처리, 아니면 다음 핸들러에게 전달
- `set_next(handler)` → 다음 핸들러 연결

**체인 구성** — 핸들러들을 순서대로 연결한다.
- `handler1` → `handler2` → `handler3` → ...
- 요청은 체인을 따라 흘러가며, 처리할 수 있는 핸들러를 만나면 멈춘다

## 주의할 점

- **요청이 처리되지 않을 수 있음**: 체인 끝까지 갔는데 아무도 처리 안 하면 요청이 사라짐. 마지막에 기본 핸들러를 두는 것이 안전
- **디버깅 어려움**: 어떤 핸들러가 처리했는지 추적이 필요할 수 있음. 로깅 추가 고려
- **체인 순서가 중요**: 핸들러 순서에 따라 결과가 달라질 수 있음
