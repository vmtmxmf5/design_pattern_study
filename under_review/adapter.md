# Adapter Pattern

## 한 줄 정의

인터페이스(메서드 이름과 호출 방식)가 맞지 않는 클래스를 중간에서 변환해서, 기존 코드 수정 없이 함께 쓸 수 있게 해주는 패턴. 흔히 쓰는 충전기 어댑터(110V → 220V)와 같은 개념이다.

## 언제 사용하는가

- **외부 라이브러리를 우리 코드에 끼워 맞출 때**: 외부 API의 메서드 이름이나 호출 방식이 우리 시스템과 다르지만, 외부 코드를 직접 수정할 수 없는 경우
- **여러 외부 서비스를 하나의 인터페이스로 묶을 때**: Slack, 카카오톡, 이메일처럼 각각 다른 API를 동일한 방식으로 호출하고 싶은 경우
- **레거시 코드를 새 시스템에 연결할 때**: 잘 동작하는 기존 코드를 새로운 설계에 맞춰 활용하고 싶지만, 인터페이스가 안 맞는 경우

### 실제 사용 사례

- 외부 결제 API 통합 (각 결제사마다 다른 API → 하나의 `pay()` 인터페이스로 통일)
- 데이터 포맷 변환 (XML 시스템 → JSON 시스템 연결)
- 알림 채널 통합 (이메일, Slack, 카카오톡을 하나의 `send()`로 호출)
- Head First 예제: Turkey의 `gobble()`을 Duck의 `quack()`으로 변환

## 핵심 구조

**Target** — 우리 코드가 사용하는 인터페이스. 예제에서는 `NotificationSender.send()`.

**Adaptee** — 메서드 이름이 다른 기존 클래스. 예제에서는 `SlackAPI.post_message()`, `KakaoAPI.send_talk()`.

**Adapter** — Target 인터페이스를 구현하면서, 내부에서 Adaptee의 메서드를 대신 호출해준다(위임). 클라이언트는 Adaptee의 존재를 모른다.

- `Client` → `Target.send()` 호출
- `Adapter.send()` → 내부에서 `Adaptee.post_message()`로 변환하여 호출

## 주의할 점

- **Adapter 안에 비즈니스 로직을 넣지 말 것**: Adapter는 인터페이스 변환만 담당한다. 로직이 섞이면 역할이 불분명해진다
- **양방향 Adapter는 복잡해진다**: 양쪽 인터페이스를 모두 구현하면 유지보수가 어려우니 꼭 필요한 경우에만 쓸 것
- **Decorator와 혼동하지 말 것**: Decorator는 같은 인터페이스에 기능을 덧붙이는 것이고, Adapter는 다른 인터페이스로 바꾸는 것
- **Facade와 혼동하지 말 것**: Facade는 복잡한 시스템을 간단하게 묶는 것이고, Adapter는 안 맞는 인터페이스를 맞추는 것
