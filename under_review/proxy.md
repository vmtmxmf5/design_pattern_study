# Proxy Pattern

## 한 줄 정의

실제 객체 대신 대리인(Proxy)을 세워서, 접근을 제어하거나 부가 작업(캐싱, 권한 검사, 지연 로딩 등)을 수행하는 패턴. 경비원이 건물 출입을 통제하는 것과 같다.

## 언제 사용하는가

- **무거운 객체의 생성을 미루고 싶을 때**: 대용량 이미지, DB 커넥션처럼 생성 비용이 큰 객체를 실제 필요한 시점까지 지연 (가상 프록시)
- **접근 권한을 제어해야 할 때**: 사용자 역할에 따라 메서드 호출을 허용하거나 차단 (보호 프록시)
- **캐싱을 투명하게 끼워 넣고 싶을 때**: 같은 요청에 대해 실제 호출 없이 캐시에서 반환
- **원격 객체를 로컬처럼 사용하고 싶을 때**: 다른 서버의 객체를 같은 프로세스에 있는 것처럼 호출 (원격 프록시)

### 실제 사용 사례

- ORM의 Lazy Loading (Django QuerySet이 실제 쿼리 실행을 지연)
- API Gateway (인증/인가 검사 후 실제 서비스에 요청 전달)
- 웹 프록시 서버 (캐싱, 접근 제어)
- gRPC 클라이언트 스텁 (원격 호출을 로컬 메서드처럼 사용)

## 핵심 구조

**동일한 인터페이스** — Proxy는 실제 객체(RealSubject)와 같은 인터페이스를 구현한다. 클라이언트는 Proxy인지 실제 객체인지 구분 못 함.

**접근 가로채기** — 클라이언트 요청이 Proxy를 먼저 거친다. Proxy가 부가 작업(권한 검사, 캐시 확인, 지연 생성 등)을 수행한 뒤, 실제 객체에게 요청을 위임.

- `Client` → `Proxy.request()` → 부가 작업 → `RealSubject.request()`

Decorator와 구조는 비슷하지만 목적이 다르다. Decorator는 기능 추가, Proxy는 접근 제어.

## 주의할 점

- **Decorator와 혼동 주의**: 구조가 거의 동일하지만, Proxy는 접근 제어가 목적이고 Decorator는 기능 추가가 목적
- **투명성 원칙**: Proxy를 쓰든 실제 객체를 쓰든 동일하게 동작해야 함. Proxy가 인터페이스를 바꾸면 안 됨
- **캐시 무효화**: 캐싱 프록시를 쓸 때 캐시 만료 정책을 반드시 고려할 것
- **단순한 경우에는 불필요**: 접근 제어나 지연 로딩이 필요 없다면 Proxy를 도입할 이유가 없음
