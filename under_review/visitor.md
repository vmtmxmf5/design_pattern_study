# Visitor Pattern

## 한 줄 정의

객체 구조를 변경하지 않고, 새로운 연산을 별도의 Visitor 클래스에 정의하여 추가할 수 있게 하는 패턴.

## 언제 사용하는가

- **기존 클래스를 수정하지 않고 새로운 연산을 추가해야 할 때**: 요소 클래스는 안정적이지만, 연산은 자주 추가되는 경우
- **복잡한 객체 구조의 모든 요소에 대해 연산을 수행해야 할 때**: 트리, 그래프 같은 구조를 순회하며 각 요소 타입에 맞는 처리를 해야 하는 경우
- **관련 없는 연산을 요소 클래스에 넣고 싶지 않을 때**: 핵심 로직과 부가 연산(XML 변환, 통계 수집 등)을 분리하고 싶은 경우

### 실제 사용 사례

- 보험 설계사 — 주택, 은행, 카페 등 다른 유형의 건물을 방문하며 각각에 맞는 보험 상품을 제안
- 컴파일러 AST 순회 — 구문 트리의 각 노드 타입에 대해 타입 체크, 코드 생성, 최적화 등 다른 연산 수행
- 문서 내보내기 — 같은 문서 구조에 대해 PDF 변환, HTML 변환, 텍스트 변환 등 다른 처리

## 핵심 구조

**이중 디스패치(Double Dispatch)** — 요소가 `accept(visitor)`를 호출하면, visitor의 적절한 메서드로 자신을 넘긴다.

- `Element.accept(visitor)` → `visitor.visit_element(self)` 호출
- `Visitor`는 요소 타입별로 `visit_xxx()` 메서드를 구현

새로운 연산을 추가하려면 새 Visitor 클래스만 만들면 된다. 기존 요소 클래스는 수정하지 않는다.

## 주의할 점

- **요소 클래스가 자주 바뀌면 부적합**: 새 요소 타입이 추가되면 모든 Visitor를 수정해야 함. 연산이 자주 추가되는 경우에만 유리
- **캡슐화 약화**: Visitor가 요소의 내부 데이터에 접근해야 할 수 있어서, 요소의 public 인터페이스가 넓어질 수 있음
- **Python에서는 `functools.singledispatch`로 대체 가능**: 타입별 분기를 데코레이터로 간결하게 처리할 수 있음
