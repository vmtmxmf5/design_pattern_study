# Bridge Pattern

## 한 줄 정의

하나의 큰 클래스를 "무엇을 할지"와 "어떻게 할지" 두 계층으로 분리하여, 각각 독립적으로 확장할 수 있게 하는 패턴.

## 언제 사용하는가

- **두 가지 독립적인 변화 축이 있을 때**: 예를 들어 "도형 종류(원, 사각형)"와 "렌더링 방식(OpenGL, DirectX)"이 각각 늘어나면, 상속만으로는 클래스가 조합 수만큼 폭발함
- **런타임에 구현을 교체해야 할 때**: 추상 계층은 그대로 두고 구현 객체만 바꿔 끼울 수 있음
- **플랫폼 독립적인 코드를 만들 때**: 상위 로직은 공통으로 유지하고, OS/API별 구현만 분리

### 실제 사용 사례

- TV 리모컨(추상) + TV 기기(구현) — 리모컨 기능 추가와 TV 브랜드 추가가 독립적
- GUI 프레임워크 — 위젯(버튼, 텍스트) × 플랫폼(Windows, macOS, Linux)
- 데이터 접근 계층 — 비즈니스 로직 × DB 드라이버(PostgreSQL, MySQL)

## 핵심 구조

**"무엇을 할지" 계층** — 고수준 제어 로직을 담당. 구현 객체를 가지고 있고, 실제 작업을 맡긴다(위임).

**"어떻게 할지" 계층** — 실제 동작을 담당. 위 계층이 호출하는 메서드를 구현한다.

- `Abstraction` → `self._impl.operation()` 위임
- 새로운 추상(리모컨 종류)이나 새로운 구현(TV 브랜드)을 추가해도 상대 계층 수정 불필요

## 주의할 점

- **변화 축이 하나뿐이면 과함**: 독립적으로 확장할 축이 두 개 이상일 때만 의미 있음
- **초기 설계가 복잡**: 어디서 추상과 구현을 나눌지 판단이 필요
- **Adapter와의 차이**: Adapter는 이미 만들어진 호환 안 되는 코드를 연결하는 것이고, Bridge는 처음부터 독립적 확장을 위해 설계하는 것
