# Composite Pattern

## 한 줄 정의

개별 객체(파일)와 복합 객체(폴더)를 같은 메서드로 다루는 패턴. 폴더 안에 파일과 하위 폴더가 섞여 있어도, `get_size()` 하나로 전체 크기를 구할 수 있다.

## 언제 사용하는가

- **트리 구조를 표현해야 할 때**: 폴더-파일, 메뉴-서브메뉴처럼 재귀적인 포함 관계가 있는 경우
- **개별 항목과 그룹을 구분 없이 처리하고 싶을 때**: 단일 파일이든 폴더든 `get_size()` 같은 메서드를 동일하게 호출하고 싶은 경우
- **트리 전체에 일괄 연산을 적용해야 할 때**: 크기 합산, 출력, 검색 등을 한 번의 호출로 재귀적으로 수행

### 실제 사용 사례

- 파일 시스템 (파일과 디렉터리의 재귀 구조)
- 메뉴 시스템 (메뉴 항목과 서브메뉴를 동일하게 처리)
- GUI 위젯 트리 (버튼은 단일 위젯, 패널은 위젯 컨테이너)
- 조직도 (직원과 부서의 계층 구조)

## 핵심 구조

**Component** — 단말 노드(Leaf)와 복합 노드(Composite) 모두가 구현하는 공통 인터페이스.

**Leaf** — 실제 작업을 수행하는 말단 객체. 예제에서는 `File`.
- `Leaf.operation()` → 자기 자신의 작업을 직접 수행

**Composite** — 자식 Component들을 관리하는 복합 객체. 예제에서는 `Directory`.
- `Composite.add(component)` / `remove(component)` → 자식 관리
- `Composite.operation()` → 모든 자식의 `operation()`을 재귀 호출

## 주의할 점

- **Leaf에 불필요한 메서드 노출**: `add()`/`remove()`를 공통 인터페이스에 넣으면 Leaf에서도 보임. 투명성과 안전성 사이에서 판단 필요
- **과도한 일반화**: 단순한 리스트로 충분한 상황에 Composite를 쓰면 불필요한 복잡성이 생김. 재귀적 트리 구조가 명확할 때만 적용
- **양방향 참조 주의**: 자식에서 부모로 거슬러 올라가야 한다면, 부모 참조의 메모리 관리에 주의
