# Template Method Pattern

## 한 줄 정의

알고리즘의 뼈대(전체 흐름)를 상위 클래스(부모)에서 정의하고, 세부 단계의 구현은 하위 클래스(자식)에 맡기는 패턴.

## 언제 사용하는가

- **알고리즘의 전체 흐름은 고정하되, 특정 단계만 바꾸고 싶을 때**: 예를 들어 데이터 마이닝에서 "파일 열기 → 파싱 → 분석 → 보고서 생성" 흐름은 같지만, 파일 형식(CSV/PDF/DOC)에 따라 파싱 방식만 다른 경우
- **여러 클래스에 비슷한 알고리즘이 중복될 때**: 공통 부분을 상위 클래스로 올리고, 다른 부분만 하위 클래스에서 오버라이드
- **하위 클래스가 알고리즘 전체를 바꾸는 것을 방지하고 싶을 때**: 특정 단계만 확장 가능하도록 제한

### 실제 사용 사례

- 건축 설계도 — 전체 공정(기초 → 골조 → 배관 → 마감)은 동일하되 세부 자재/공법은 다름
- 프레임워크 훅 — Django의 `View` 클래스에서 `get()`, `post()`만 오버라이드
- 테스트 프레임워크 — `setUp()` → `runTest()` → `tearDown()` 흐름은 고정, 각 단계를 오버라이드

## 핵심 구조

**Template Method** — 상위 클래스에 정의된 알고리즘 뼈대. 순서대로 각 단계 메서드를 호출한다. 하위 클래스가 이 메서드 자체를 오버라이드하는 것은 금지.

**추상 단계** — 하위 클래스가 반드시 구현해야 하는 메서드.

**훅(Hook)** — 기본 구현이 비어있는 선택적 메서드. 하위 클래스가 필요할 때만 오버라이드. 없어도 되고 있어도 되는 확장 포인트.

- 상위 클래스: `template_method()` → `step1()` → `step2()` → `hook()` → `step3()` 순서 고정
- 하위 클래스: `step1()`, `step2()` 구현 + 필요시 `hook()` 오버라이드

## 주의할 점

- **Strategy 패턴과의 차이**: Template Method는 상속으로 단계를 교체하고, Strategy는 조합으로 알고리즘 전체를 교체
- **Factory Method와의 관계**: Factory Method는 Template Method의 특수한 형태로 볼 수 있음 (생성 단계를 하위 클래스에 위임)
- **단계가 많아지면 유지보수 어려움**: 오버라이드 가능한 단계가 많으면 하위 클래스 작성자가 어떤 단계를 구현해야 하는지 파악하기 어려움
