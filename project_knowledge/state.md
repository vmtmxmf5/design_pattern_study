# State Pattern

## 한 줄 정의

객체의 내부 상태를 별도의 클래스로 분리하여, 상태가 바뀌면 행동도 자동으로 바뀌게 하는 패턴.

## 언제 사용하는가

- **같은 메서드가 상태에 따라 완전히 다르게 동작해야 할 때**: 예를 들어 문서의 `publish()`가 초안이면 검토 요청, 검토 중이면 공개, 이미 공개됐으면 아무것도 안 하는 경우
- **상태별 조건 분기(if/switch)가 여러 메서드에 반복될 때**: 상태가 추가될 때마다 모든 메서드의 모든 분기를 수정해야 하는 문제를 해결
- **상태 전환 규칙이 정해져 있을 때**: 특정 상태에서 특정 상태로만 전환 가능하고, 잘못된 전환을 방지해야 하는 경우 (예: 결제 전에 배송 불가)
- **상태 추가/변경이 빈번할 때**: 새 상태 클래스를 추가해도 기존 상태 클래스를 수정할 필요 없음 (Open/Closed Principle)

### 실제 사용 사례

- 주문 처리 시스템 (대기 → 결제완료 → 배송중 → 완료/취소)
- 문서 승인 워크플로우 (초안 → 검토중 → 승인/반려)
- 스마트폰 버튼: 잠금 상태에서는 잠금 해제 화면, 해제 상태에서는 기능 실행, 배터리 부족이면 충전 화면
- 미디어 플레이어 (정지 → 재생 → 일시정지)
- 네트워크 연결 (끊김 → 연결 중 → 연결됨)
- 뽑기 기계 — 동전 없음 → 동전 투입 → 손잡이 돌림 → 상품 배출 → (재고 없음) 상태를 if/else로 관리하면, 새 기능(10% 확률 보너스) 추가 시 모든 메서드를 수정해야 함

## 핵심 구조

**상태 캡슐화** — 각 상태 클래스가 "이 상태일 때의 행동"을 들고 있다. Context(예: 뽑기 기계)는 행동을 직접 구현하지 않고, 요청이 오면 현재 상태 객체에게 넘긴다. 같은 메서드 호출이라도 현재 상태 객체가 다르면 행동이 달라진다.

**상태 전환** — 상태 클래스가 행동을 수행한 뒤, 다음 상태를 직접 결정하여 Context의 상태를 교체한다. Context가 아니라 상태 클래스가 전환을 주도한다.

- 클라이언트 → `Context.request()` 호출
- Context → `self._state.handle(self)` 넘김
- State → 행동 수행 + `context.set_state(next_state)` 전환

### Strategy 패턴과의 차이

- **Strategy**: 클라이언트가 알고리즘을 직접 선택하여 교체. Strategy 객체들은 서로를 모름
- **State**: 상태 전환이 내부에서 자동으로 발생. State 객체들이 서로를 알고, 다음 상태로의 전환을 직접 수행

## 주의할 점

- **상태 수가 적고 전환이 단순하면 과한 패턴**: 상태가 2~3개이고 전환 규칙이 단순하다면 if/else가 더 읽기 쉬움
- **상태 전환 로직의 위치**: State 클래스 안에 두면 상태 간 의존이 생기고, Context에 두면 Context가 비대해짐. 전환 규칙이 복잡하면 별도의 전환 테이블을 고려
- **상태 객체 공유**: 상태 객체가 자체 데이터를 가지지 않는다면 싱글턴으로 공유하여 불필요한 객체 생성을 줄일 수 있음
- **모든 상태에 모든 메서드를 구현해야 함**: 특정 상태에서 의미 없는 메서드도 구현해야 하므로, 빈 메서드나 예외 처리가 늘어날 수 있음
